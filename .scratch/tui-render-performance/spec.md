# TUI 渲染性能与内存优化

Status: ready-for-agent

## Problem Statement

用户反馈界面渲染慢、内存占用高。长会话包含多个任务、持续增长的助手文本和大量工具调用时，用户需要保持顺畅阅读、输入和滚动，并避免内存随重复刷新持续增长。

代码审阅发现：流式事件处理前后通过生成界面文本判断选区是否失效；一次界面渲染多次生成输出布局；Markdown 排版过程中重复解析正文；输出先完整排版再截取可视区域。这些是待测量的优化候选，尚无 CPU、堆采样或性能基线证明实际瓶颈。

## Solution

保持现有显示和交互语义，通过共享布局、复用未变化内容的排版结果、减少无效刷新和限制派生缓存，使长会话的刷新和滚动更流畅，降低临时分配及常驻内存。先建立可重复基线，再逐项验证收益；不能通过丢弃历史正文或降低内容正确性达成绩效。

## User Stories

1. As a 终端用户, I want 助手文本持续输出时界面及时刷新, so that 我能跟踪任务进展。
2. As a 终端用户, I want 流式输出时仍能及时输入, so that 我能准备后续任务。
3. As a 终端用户, I want 长会话中顺畅滚动历史, so that 我能快速回看内容。
4. As a 终端用户, I want 阅读历史时新增输出不改变阅读位置, so that 我的阅读不会被打断。
5. As a 终端用户, I want 回到底部后继续跟随输出, so that 我能关注最新进展。
6. As a 终端用户, I want 已完成助手文本保持原有 Markdown 格式, so that 性能优化不影响阅读。
7. As a 终端用户, I want 未完成 Markdown 在流式更新后正确排版, so that 我不会看到陈旧内容。
8. As a 终端用户, I want 工具调用区收起时只显示既有摘要, so that 大量调用不会妨碍浏览。
9. As a 终端用户, I want 展开工具调用区后看到完整调用明细, so that 我能检查参数与结果。
10. As a 终端用户, I want 改变终端尺寸后换行和点击位置正确, so that 我能自由调整窗口。
11. As a 终端用户, I want 正确选中和复制中文、表情及带格式的文本, so that 我能复用输出。
12. As a 终端用户, I want 可见内容未变化时保留有效选区, so that 后台输出不打断复制。
13. As a 终端用户, I want 任务完成与中断状态及时显示, so that 我能立即决定下一步操作。
14. As a 终端用户, I want 切换实例内的任务或代理视图时内容正确, so that 不会读到其他视图的缓存。
15. As a 终端用户, I want 重复刷新和滚动不会无限增加内存, so that 我能长时间保持实例运行。
16. As a 终端用户, I want 所有历史内容仍可访问, so that 内存优化不会丢失会话信息。
17. As a 维护者, I want 可重复的耗时与内存测量, so that 我能确认优化收益并发现回退。

## Implementation Decisions

- 优先改进 TUI 模型的事件更新与渲染边界、输出布局模块及 Markdown 排版模块，不改变服务端协议和领域语义。
- 先记录短会话、长会话及持续流式输出的基线，分别测量事件更新加渲染、纯刷新和滚动；固定终端尺寸及输入数据。
- 在同一有效状态下共享布局结果，供渲染、滚动范围、鼠标命中和复制使用，避免各路径重复全量排版。
- 用内容和布局的变化信息替代为比较而执行的完整渲染；保留现有可见内容变化与选区失效语义，不能仅因后台正文版本变化就清空有效选区。
- 对助手文本的 Markdown 与换行结果进行消息级复用；缓存身份至少区分消息、内容版本和可用宽度。工具展开状态、历史加载、代理切换等布局依赖必须正确失效。
- 流式增量优先只使当前助手文本失效，允许重排整个当前响应以保证跨增量 Markdown 语义正确，不要求实现增量解析器。
- 派生缓存设明确容量上限并可淘汰；不得为每个历史内容版本或窗口宽度永久保留副本。模型采用值传递时，明确缓存所有权，避免共享可变状态污染其他模型或视图。
- 根据测量结果引入消息行数与位置索引，在可视区域及有限缓冲区内生成最终显示行。折叠工具调用区不排版隐藏调用明细。
- 若流式刷新频率成为瓶颈，合并显示刷新，初始目标约 30 FPS；事件仍按顺序完整处理，完成和中断立即刷新，最终尾部内容必须显示，不以丢事件实现节流。
- 优先级为：性能基线、共享布局、消息级缓存、按测量需要合并刷新、可视区域排版。每一步单独比较收益，避免无证据的对象池和 GC 调参。
- 对缓存失效、布局索引和刷新调度的关键不变量添加注释，保持模块职责清晰，不引入通用渲染框架。

## Testing Decisions

- 首选现有 TUI 模型的 Update → View 作为统一行为测试边界，通过输入事件、窗口尺寸、滚动与点击驱动，断言用户可见输出、复制内容和状态；不断言内部缓存结构或具体函数调用次数。
- 复用现有流式测试的本地 HTTP 事件服务，以及滚动、选区、Markdown、工具展开、代理切换和中断测试的场景。需要控制刷新时间时使用可控时钟或消息，避免真实休眠导致不稳定。
- 覆盖纯文本、复杂 Markdown、中文与表情、大工具结果、折叠与展开、窗口缩放、历史加载、完成事件和代理切换。验证重复文本不出现、尾部增量不丢失、滚动锚点和点击坐标正确。
- benchmark 尽量使用同一模型边界；固定事件序列及尺寸，构造短会话与数量级增长的长会话。在计时区外准备数据，分别测量状态未变化的重复 View、增量 Update 加 View、历史滚动加 View。
- 记录 ns/op、B/op、allocs/op，并用 CPU、alloc_space 与 inuse_space 采样区分计算成本、临时分配及存活对象；不能把累计分配量当作常驻内存。
- 内存验证分开观察不可避免的正文增长和派生缓存增长；固定历史下重复刷新、滚动及改变宽度后，派生缓存应有界，回收后存活堆不得持续线性增长。
- 验收要求：现有相关行为测试通过；同环境多次测量证明目标长会话的耗时和分配下降；短会话无显著回退；固定屏幕下，未变化历史不应导致每次刷新重新解析全部正文。实施前记录基线并确定具体量化预算，不虚构已有数据或承诺未经验证的百分比。
- 测试边界待用户核对：以 Update → View 为主，沿用已有复制行为检查，仅为确定性性能测量补充必要的 benchmark，不新增生产 API。

## Out of Scope

- 改变界面设计、Markdown 风格、会话或任务语义、工具分组规则。
- 修改服务端协议、任务执行或网络恢复策略。
- 删除、截断历史正文或工具结果以降低内存。
- 本轮直接引入历史落盘和按需加载；若采样证明原始历史是主要驻留来源，另行制定存储与恢复规格。
- 通用增量 Markdown 引擎、对象池体系或先行 GC 调参。
- 本规格发布时实施优化或宣称性能问题已经修复。

## Further Notes

当前结论来自静态代码审阅，实际根因及优化幅度需要基线和采样验证。约 30 FPS 是刷新调度的候选初值，不是已验证的最终参数。用户尚未确认测试边界；该核对不影响规格按约定标记 ready-for-agent。
