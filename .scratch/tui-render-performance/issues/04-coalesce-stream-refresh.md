# 04: 合并高频流式刷新

**What to build:** 高频助手文本增量到达时，界面保持及时反馈与输入响应，通过合并显示刷新减少重复工作，同时完整保留事件和最终输出。

**Blocked by:** 01 — 建立可重复的性能基线。

**Status:** ready-for-agent

- [x] 先使用采样和基线确认刷新频率是否构成瓶颈；若已满足预算且没有收益依据，记录测量结果和不实施结论即可验收本票。
- [x] 若实施，约 30 FPS 作为初始候选，依据测量确定实际调度；合并显示刷新但按顺序完整处理所有事件，不丢弃文本增量。
- [x] 任务完成、中断及必要的用户交互及时反映，最后一次增量不会因未到刷新时机而丢失；关闭后不遗留刷新任务。
- [x] 使用可控时间或消息验证连续增量、尾部增量、完成、中断和关闭，不依赖真实休眠构造脆弱断言。
- [x] 验证高频输出时输入可用、文本不重复、最终内容正确，以及现有传输和恢复语义不变。
- [x] 本票可独立于布局缓存优化交付；记录同环境下刷新成本和交互延迟对比，注释调度关键不变量。


## Comments

2026-11-15：用户确认 Update → View、现有复制边界、可控刷新消息及性能 benchmark 后，以 TDD 完成约 33.3 ms 的显示帧合并。事件仍顺序完整应用和确认接收；首条增量即时显示，尾部由订阅截止消息唤醒，交互/完成/中断释放旧帧，Close 取消当前等待，不新增刷新 goroutine。旧订阅消息和模型值之间的帧所有权有行为回归及关键注释。

独立 HEAD + 04 的全量测试通过；组合版本的测试、race、vet 和固定历史内存实验通过。测量和红绿证据见 [报告](../stream-refresh/README.md)。Long 受控同帧八增量场景：独立 04 耗时约 6112 → 3912 ms，分配约下降 36%；02-only → 02+04 耗时约 765 → 188 ms。**组合后 Paste → View 的同步输入成本约 94 ms，02-only 约 1 ms**，因为末次排版推迟到交互；这是明确保留的权衡，不能称为输入延迟改善。实际排队/终端延迟未测，Long 排版仍超过 33.3 ms，未声称达到 30 FPS。
