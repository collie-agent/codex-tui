# 实例内会话延续、中断与继续

Status: ready-for-agent

## Problem Statement

用户需要在一个 TUI 实例中连续推进同一会话，并能在任务运行期间按 ESC 中断，在中断后输入新的要求继续工作。已有实例内会话延续与 --conv-id 启动能力已经实现，但 TUI 尚未保存当前运行 ID、调用中断接口或识别中断终态，因此用户无法从界面可靠地停止任务并继续。

中断请求被接受不代表执行已经停止或中断进度已经保存。如果过早允许下一次执行，新任务可能读不到刚刚中断的进度；如果只等待正常完成事件，中断后的界面又可能一直无法继续。用户还需要保留已有输出和编辑中的草稿，且断线、重复按键及迟到响应不能改变会话归属或误解锁下一次提交。

## Solution

一个实例中的任务归属于同一会话。普通启动时，首个任务建立会话，后续任务沿用该会话；通过 --conv-id 可以从首次提交起延续指定会话。每个任务都独立验证服务端返回的会话归属。

运行期间按 ESC 请求中断当前运行；尚未收到运行 ID 时先记录中断意图，待收到后立即发送请求。界面区分等待运行开始、请求中断、等待终态、已中断和请求失败。收到服务端确认执行停止且中断进度保存完成的终态事件后，保留全部已有输出与草稿，允许用户按 Enter 提交新输入，在原会话中启动下一次任务。

本规格中的“恢复”统一表述为“中断后继续”：携带原会话 ID 和新输入创建新运行，参考服务端已保存的进度；不表示从原 ReAct 执行位置恢复，也不复用原运行 ID。

## User Stories

1. As a 终端用户, I want 普通启动后直接输入首个任务, so that 无需提前创建会话。
2. As a 终端用户, I want 首个任务返回后自动关联会话, so that 不必手工复制会话 ID。
3. As a 终端用户, I want 后续任务延续同一会话, so that 服务端能够引用前序任务的结果和错误。
4. As a 终端用户, I want 使用 --conv-id 指定已有会话, so that 新实例可以继续此前工作。
5. As a 终端用户, I want 指定会话后的首次提交就携带该会话 ID, so that 不会意外创建新会话。
6. As a 终端用户, I want 指定会话启动时看到空白输入界面, so that 可以直接提出新任务。
7. As a 终端用户, I want 状态栏显示当前会话 ID, so that 能确认当前工作的归属。
8. As a 终端用户, I want 普通重启时开始新会话, so that 不会隐式恢复上次实例的身份。
9. As a 终端用户, I want 每次任务都验证返回的会话信息, so that 本地配置不会被误当成服务端确认。
10. As a 终端用户, I want 任务结束但没有有效会话信息时看到原因并禁止再提交, so that 不会静默丢失上下文。
11. As a 终端用户, I want 返回会话与绑定会话冲突时保留原会话并阻止后续提交, so that 不会被自动切换到其他会话。
12. As a 终端用户, I want 入队成功、正常完成与中断完成有明确区别, so that 不会误判执行结果。
13. As a 终端用户, I want 无效会话不触发自动创建新会话, so that 输入错误不会改变工作归属。
14. As a 终端用户, I want 当前任务结束前禁止重复提交且仍能编辑草稿, so that 保持串行执行并提前准备下一步。
15. As a 终端用户, I want 断线续传和重复事件不改变会话归属, so that 网络恢复后仍能连续工作。
16. As a 终端用户, I want 前一任务的迟到消息不影响当前任务, so that 当前任务的归属验证可靠。
17. As a 终端用户, I want 已有任务输出与阅读交互继续可用, so that 延续会话不会损害浏览体验。
18. As a 终端用户, I want 在任务运行期间按 ESC 请求中断, so that 可以停止当前执行并调整后续要求。
19. As a 终端用户, I want 输入框已有草稿时 ESC 仍然请求中断且保留草稿, so that 不会丢失准备好的后续要求。
20. As a 终端用户, I want 浏览历史输出时 ESC 优先请求中断, so that 中断操作不依赖当前滚动位置。
21. As a 终端用户, I want 没有运行时 ESC 保留原有的回到底部行为, so that 已有阅读操作继续可用。
22. As a 终端用户, I want 任务已提交但尚无运行 ID 时 ESC 记录中断意图, so that 不必反复等待并重新按键。
23. As a 终端用户, I want 排队期间看到“等待运行开始后中断”, so that 不会误以为排队任务已经被取消。
24. As a 终端用户, I want 收到运行 ID 后自动发送已记录的中断请求, so that 我的中断意图能及时执行。
25. As a 终端用户, I want 中断请求进行中重复 ESC 不产生重复请求, so that 操作保持可预测。
26. As a 终端用户, I want 请求被接受后看到等待终态的状态, so that 不会误把请求送达当成执行停止。
27. As a 终端用户, I want 中断请求失败时看到原因并保留草稿, so that 可以判断问题并手动重试。
28. As a 终端用户, I want 请求失败后再次 ESC 手动重试, so that 无需重启界面。
29. As a 终端用户, I want 网络错误或运行已结束的 HTTP 响应不直接解锁下一次执行, so that 不会与尚未确认停止的运行重叠。
30. As a 终端用户, I want 收到中断终态后看到“已中断”, so that 能确认执行已经停止且进度已经保存。
31. As a 终端用户, I want 中断后保留全部已有输出, so that 可以根据已完成的工作决定下一步。
32. As a 终端用户, I want 中断后按 Enter 提交新输入并沿用原会话, so that 可以参考已保存进度继续工作。
33. As a 终端用户, I want 下一次任务继续追加输出, so that 可以在同一界面回看整个工作过程。
34. As a 终端用户, I want 没有主动按 ESC 时收到中断终态也能正确展示, so that 界面与服务端实际结果保持一致。
35. As a 终端用户, I want 运行抢先正常完成时显示正常完成, so that 不会被迟到的中断响应错误标记为已中断。
36. As a 终端用户, I want 中断终态先于 HTTP 响应到达时立即按终态处理, so that 不必多等一次响应。
37. As a 终端用户, I want 中断期间断线后继续接收回放事件, so that 不会因为网络波动丢失终态确认。
38. As a 终端用户, I want 长期收不到终态时界面继续等待且允许编辑草稿, so that 不会因超时猜测而并行启动新任务。
39. As a 终端用户, I want 保留既有退出方式, so that 可以离开仍在等待的界面。
40. As a 终端用户, I want 明确中断不撤销工具已产生的操作, so that 不会把中断误认为回滚。

## Implementation Decisions

### 已有会话延续约束

- 实例对应一次 TUI 进程生命周期；会话身份仅存于进程内，不新增本地持久化。
- 保留 --conv-id 启动能力，不恢复旧的 --task-id 命令行入口。空值按未指定会话处理；内部仍使用任务 ID 订阅新任务。
- 指定会话启动时不查询或加载历史输出，不自动创建任务或订阅旧任务；显示空白输入界面和指定的会话 ID。
- POST /tasks 使用 input 和可选的 conv_id。无会话时首次提交省略 conv_id；绑定后所有提交均携带同一值，与当前服务端 HTTP 字段保持一致；ConvId 仅用于服务端内部队列。
- 创建响应中的 task_id 用于订阅本次任务。task_info 的 Delta 为第二层 JSON，包含 run_id 与 conv_id；三个身份各司其职，不相互替代。
- 分别维护实例绑定的会话身份与当前任务的归属确认。每次创建新任务都重新等待当前任务的有效确认；指定 --conv-id 不等于服务端确认。
- 未绑定时由首个有效 task_info 的非空 conv_id 绑定会话；已绑定时必须匹配。重复的一致信息不改变身份。
- 正常完成或中断终态到达时，若本任务没有有效会话归属确认，显示缺失信息错误并阻止后续提交。无效 JSON、空 conv_id 不能构成有效确认。
- 会话冲突时保留原身份、显示协议异常并阻止后续提交；重连、重复信息和任何终态都不能清除此限制。
- HTTP 201 只表示任务入队。无效会话或消费者失败时沿用现有等待及连接错误处理，不自动新建会话，不宣称任务成功或会话验证成功。
- 保留串行提交、创建失败手动重试和草稿保护。状态栏继续显示当前会话 ID；服务端上下文延续不等于完整聊天历史恢复。

### 中断协议与状态

- 本轮修改 TUI 的输入处理、当前任务状态、HTTP 请求、SSE 终态处理和状态展示；使用 codex-go 已有接口及事件，不修改服务端、不引入数据库或新的外部接口。
- 当前任务保存来自 task_info 的 run_id，仅用于中断当前运行；开始下一任务时清理上一任务的运行身份、中断意图和请求状态，保留会话身份。
- 运行期间 ESC 优先请求中断，不受草稿或输出滚动位置影响；不清空草稿或已有输出。没有运行时，ESC 保留原有回到底部行为。
- 创建请求进行中或任务已入队但尚无 run_id 时，ESC 记录本任务的中断意图，显示“等待运行开始后中断”。收到 run_id 后立即发送中断请求，不宣称排队任务已取消。
- 使用 POST /runs/{run_id}/interrupt，无请求体。该接口中断整个根运行；不得将 task_id 或 conv_id 放入运行 ID 的位置。
- 区分等待运行身份、请求进行中、请求已接受且等待终态、请求失败和任务终态。中断请求进行中重复 ESC 不重复发送；已接受后继续等待终态。
- HTTP 202、status=accepted 只确认请求被执行者接收；HTTP 409、status=already_requested 也进入等待终态，不显示“已中断”。
- HTTP 409、status=terminal 仅提示运行已结束但终态待确认，继续等待原 SSE；不能据此推断已保存为 interrupted，也不能解锁下一次执行。
- HTTP 404、503、网络错误及其他失败显示原因、保留草稿并允许再次 ESC 手动重试，不自动重新发送，不解锁下一次提交。服务端错误与远端文本沿用现有终端控制字符处理。
- 原任务 SSE 的 task_interrupted 为中断终态，Delta 为 JSON 字符串“{}”；服务端仅在执行停止且 interrupted 状态保存成功后发布。此事件与 task_completed 一样带有 Stream ID，支持回放、续传与去重。
- 收到 task_interrupted 后结束当前订阅，显示“已中断”，保留输出与草稿；当前任务归属确认通过且无冲突时允许下一次提交。即使本地没有发起 ESC，也应识别服务端中断终态。
- 收到 task_completed 按正常完成处理并关闭订阅。两种终态都优先于尚未处理的中断 HTTP 响应；迟到的成功或错误响应不得覆盖终态。
- 新任务与新创建请求必须隔离前一任务的中断 HTTP 响应、SSE 事件和连接通知。旧消息不得改变新任务的身份、状态或提交权限。
- 中断等待期间继续沿用现有 SSE 断线重连、游标和去重策略；传输恢复不得清除中断等待状态或覆盖持久的会话归属错误。
- 断流、停止输出、HTTP 已接受、没有正常完成事件或超时均不表示中断完成。长期无终态时保持等待，不提供强制继续，不启动并行任务；用户仍可编辑草稿或使用既有退出方式。
- 保留 Ctrl+D 退出和 Ctrl+C 选区复制行为。退出及取消本地 HTTP/SSE 不等于服务端已经中断，不额外隐式发送中断请求。

### 中断后继续

- 收到有效终态并满足会话归属约束后，由用户再次按 Enter 提交当前草稿；终态到达不会自动执行草稿。
- 中断后继续仍使用 POST /tasks，携带新 input 和原 conv_id，不发送原 run_id。服务端创建新的 task_id 和 run_id，并参考已保存的中断进度。
- 下一次任务继续追加输出，独立等待自己的 task_info 确认；不得继承上一任务的归属确认或中断意图。
- 中断不撤销已经执行的工具操作；不增加回滚能力，也不承诺从原 ReAct 步骤继续执行。
- 在终态确认、逐任务身份、异步响应隔离和中断状态转换等关键位置添加解释约束的注释，保持模型状态、协议解析、请求发送和输出展示职责清晰，遵循 SOLID 原则；设计模式按实际职责边界选用。

## Testing Decisions

- 用户在 Q9 已确认测试边界：沿用 TUI Update/View 消息驱动与本地 HTTP/SSE 服务的集成测试。模拟按键、草稿编辑和服务端响应，观察实际请求、渲染内容、连接关闭及能否再次提交，不通过私有字段或内部函数调用证明行为。
- 现有创建任务、创建失败手动重试、连续会话、指定会话启动、SSE 回放、断线续传去重及旧订阅消息隔离测试提供先例；优先扩展这些已有边界，不新增底层测试接口。
- 保留已有会话回归：普通首次请求省略 conv_id；后续和指定会话请求携带正确值；每任务独立确认；缺失、无效或冲突归属阻止下一次提交；创建期间保护草稿与串行提交。
- 验证运行时 ESC 使用 task_info 返回的 run_id，发送正确路径与无请求体的 POST；有草稿和浏览历史输出时也优先中断，无运行时保留原滚动行为。
- 验证创建中和排队中按 ESC 不提前发送缺少身份的请求，提示等待运行开始；收到 run_id 后发送一次中断请求，重复 ESC 不产生重复请求。
- 验证 202 和 409 already_requested 后仅进入等待终态，不能再提交；409 terminal 不能代替 SSE 终态确认。
- 验证 404、503、网络错误及其他请求失败显示原因且保留草稿，不自动重试；再次 ESC 可以手动重试，失败本身不能解锁提交。
- 验证 task_interrupted 到达时关闭 SSE、显示已中断，完整保留已有输出与草稿，不自动提交；没有本地中断请求时也能识别该终态。
- 验证中断后用户按 Enter 的实际请求只有新 input 和原 conv_id，不携带原 run_id；新任务正常追加输出，并重新要求本任务归属确认。
- 验证 task_interrupted 缺少有效归属或存在会话冲突时仍阻止下一次提交；重复或迟到事件不得解除保护。
- 验证两种终态先于中断 HTTP 响应到达的竞态：正常完成保持正常完成，中断完成保持已中断；随后返回的成功和失败响应都不能覆盖终态。
- 验证下一任务创建中和运行中收到上一任务迟到的中断响应、终态或连接通知，不改变新任务的状态、归属和提交权限。
- 验证中断期间断线后按游标续传，重复事件不重复呈现输出或发送请求，回放中断终态能够结束等待；会话冲突错误与中断等待状态在重连后仍然可靠。
- 验证只有入队、请求接受、连接中断或没有输出时，不显示已中断或成功，不自动创建下一任务；长期无终态时草稿仍可编辑且 Enter 不执行。
- 回归退出、选区复制、工具输出阅读、草稿保护及重复 Enter 行为，确认本地关闭连接不额外触发服务端中断。
- 实现完成后运行相关测试、Go 全量测试、竞态检测及静态检查，并检查差异格式；本次规格整理不宣称已经执行功能验证。

## Out of Scope

- 通过原 run_id 恢复被主动中断的运行，或从原 ReAct 执行位置恢复。
- 修改服务端中断实现、新增失败事件、状态查询接口或排队取消接口。
- 客户端超时推断终态、固定延时后解锁、强制继续、并行任务或自动执行草稿。
- 撤销已产生的工具副作用或为工具操作增加回滚。
- 会话身份或待中断意图的本地持久化、自动恢复上次实例、一个实例切换或管理多个会话。
- 查询并加载会话历史输出，恢复 --task-id 命令行入口，或保证完整聊天历史恢复。
- 缺失或冲突时自动切换会话、创建替代会话，或自动重新提交任务。

## Further Notes

- 本规格保留已有会话延续约束，将中断与继续决策合并为正式要求，取代此前的设计访谈草稿及“待确认”内容。已有会话延续实现见本地 tracker 的 issues/01 至 03；本轮待实现部分是 ESC 中断、终态处理及中断后继续。
- 本次三轮访谈 Q1 至 Q9 已全部确认。用户说明 codex-go 已实现中断终态事件，重新核实最新工作区后确认 task_interrupted 契约；此前“服务端没有中断终态事件”的调查结论已撤销，不构成实现依据。
- 接口依据为 codex-go 的 codex-server 文档及当前实现。运行环境需包含已有的 task_interrupted 支持；不兼容该事件的旧服务端可能一直无法提供中断终态确认，客户端仍保持等待。
- 失败任务、进程异常、中断状态保存失败或终态事件发布失败仍可能没有终态通知；此限制不由 TUI 猜测修复。
- 规格已发布到本地 Markdown issue tracker，标记 ready-for-agent。本轮只整理规格，尚未实现中断功能；不新建或改写已有完成票，也无需新增 ADR。
