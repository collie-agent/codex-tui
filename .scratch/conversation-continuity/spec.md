# 实例内会话延续

Status: ready-for-agent

## Problem Statement

当前实例内的每次提交只发送任务输入，未消费任务返回的会话信息，因此后续任务可能创建新会话，无法引用前序任务结果。用户需要在同一实例中连续推进同一会话，也需要通过会话 ID 在新实例中继续工作。现有按任务 ID 接入的启动方式不符合这一入口需求。

## Solution

一个实例中的任务归属于同一会话。普通启动时，首次任务创建会话，之后每次提交沿用该会话。使用 `--conv-id` 可以从首次提交起延续指定会话，替代原来的 `--task-id` 入口。状态栏显示当前会话 ID；每次任务都验证服务端返回的会话归属，缺失或冲突时明确提示并阻止后续提交。

## User Stories

1. As a 终端用户, I want 普通启动后直接输入首个任务, so that 无需提前创建会话。
2. As a 终端用户, I want 首个任务返回后自动关联会话, so that 不必手工复制会话 ID。
3. As a 终端用户, I want 后续任务延续同一会话, so that 服务端能够引用前序任务的结果和错误。
4. As a 终端用户, I want 使用 --conv-id 指定已有会话, so that 新实例可以继续此前工作。
5. As a 终端用户, I want 指定会话后的首次提交就携带该会话 ID, so that 不会意外创建新会话。
6. As a 终端用户, I want 指定会话启动时看到空白输入界面, so that 可以直接提出新任务。
7. As a 终端用户, I want 状态栏显示当前会话 ID, so that 能确认当前工作的归属。
8. As a 终端用户, I want 普通重启时开始新会话, so that 不会隐式恢复上次实例的身份。
9. As a 终端用户, I want 每次任务都验证返回的会话信息, so that 本地配置不会被误当成服务端确认。
10. As a 终端用户, I want 任务完成但没有有效会话信息时看到原因并禁止再提交, so that 不会静默丢失上下文。
11. As a 终端用户, I want 返回会话与绑定会话冲突时保留原会话并阻止后续提交, so that 不会被自动切换到其他会话。
12. As a 终端用户, I want 入队成功与任务完成有明确区别, so that 不会误判会话有效性或执行结果。
13. As a 终端用户, I want 无效会话不触发自动创建新会话, so that 输入错误不会改变工作归属。
14. As a 终端用户, I want 当前任务完成前禁止重复提交且仍能编辑草稿, so that 保持串行执行并提前准备下一步。
15. As a 终端用户, I want 断线续传和重复事件不改变会话归属, so that 网络恢复后仍能连续工作。
16. As a 终端用户, I want 前一任务的迟到消息不影响当前任务, so that 当前任务的归属验证可靠。
17. As a 终端用户, I want 已有任务输出与阅读交互继续可用, so that 延续会话不会损害浏览体验。

## Implementation Decisions

- 实例对应一次 TUI 进程生命周期；会话身份仅存于进程内，不新增本地持久化。
- 命令行移除 --task-id，增加 --conv-id。不保留旧参数兼容入口。空值按未指定会话处理。
- 指定会话启动时不查询或加载历史输出，也不自动创建任务或订阅旧任务；显示输入界面和指定的会话 ID。
- 调整启动配置、TUI 模型、任务创建请求、事件处理和状态展示。沿用现有 HTTP 创建与 SSE 订阅机制，不新增服务端接口。
- POST /tasks 使用 input 和可选的 ConvId 字段。请求字段必须为 ConvId，不能误用事件字段 conv_id。无会话时首次提交省略 ConvId；绑定后所有提交均携带相同的值。
- 创建响应中的 task_id 继续用于订阅本次任务事件；移除命令行任务接入入口不代表移除内部任务 ID。
- task_info 的 Delta 是 JSON 字符串，二次解析后包含 run_id 与 conv_id。会话身份取自非空的 conv_id，不使用 task_id 或 run_id 替代。
- 分别维护实例绑定的会话身份与当前任务是否已收到有效归属确认；每次创建新任务都重新等待该任务的确认。
- 未绑定时由首个有效 task_info 绑定会话；已绑定时必须匹配，包括使用 --conv-id 启动的首个任务。相同任务重复返回一致信息不改变身份。
- task_completed 到达时，若本次任务未收到有效 task_info，显示缺失会话信息错误并阻止后续提交；即使实例已有会话 ID 也适用。
- 收到与绑定身份冲突的会话 ID 时，保留原身份，显示协议异常并阻止后续提交；不得通过后续完成事件清除该限制。
- 保留既有串行提交、草稿保护、创建错误手动重试、事件续传去重及旧任务消息隔离行为。任务完成且本次归属验证成功才允许下一次提交。
- HTTP 201 仅表示任务入队。指定会话是否存在由消费者异步检查，当前没有专用失败事件；沿用现有等待及连接错误处理，不自动新建会话，也不宣称已验证成功。
- 状态栏显示当前会话 ID；修正把每次提交描述为独立新会话的文案。后端延续的是前序运行结果和错误，不承诺完整聊天历史恢复。
- 在会话绑定、逐任务确认及冲突保护等关键逻辑处添加解释约束的注释；保持模型状态、协议解析和请求发送的职责清晰。

## Testing Decisions

- 优先沿用现有 TUI 消息驱动与本地 HTTP/SSE 服务的集成边界：模拟用户输入和服务端事件，观察请求、界面和能否再次提交，不断言私有字段或内部函数调用。
- 现有创建任务、创建失败手动重试、SSE 回放完成、断线续传去重测试提供先例；扩展这些测试覆盖连续会话，不另建底层测试接口。
- 验证普通启动的首次请求不含 ConvId，收到 task_info 并完成后第二次请求携带服务端返回的 ID。
- 验证指定会话从首次请求起携带 ConvId，启动不加载历史、不自动提交，状态栏显示指定身份。
- 验证每次任务都要求有效 task_info：首个任务缺失、后续任务缺失、指定会话首个任务缺失，以及无效 JSON 或空 conv_id 未构成有效确认时，完成后均不能继续提交。
- 验证返回会话冲突时错误可见、原 ID 保留、完成事件不能解除提交限制；一致事件重复和回放不会误报冲突。
- 验证前一任务的迟到事件不能确认或覆盖当前任务归属；创建中和运行中连续 Enter 不创建多个任务。
- 验证入队后没有归属或完成事件时，不显示验证成功或任务成功，不自动改建会话。
- 在命令行外部边界验证新参数可用、帮助文本更新、旧参数不再接受；尽量复用现有启动测试设施。
- 执行相关测试以及 Go 全量测试、静态检查，关注既有编辑、输出浏览和续传回归。
- 本轮按 to-spec 的“不访谈，直接综合”要求采用上述现有边界；该具体测试方案为规格建议，未另行取得用户逐项确认。

## Out of Scope

- 会话 ID 本地持久化、自动恢复上次实例、一个实例切换或管理多个会话。
- 按会话查询并加载历史输出，或保留 --task-id 接入入口。
- 新增服务端失败事件、状态查询、取消接口或客户端超时推断任务失败。
- 并行任务、自动重新提交、缺失或冲突时自动创建新会话。
- 恢复完整聊天历史或改变服务端上下文组织方式。
